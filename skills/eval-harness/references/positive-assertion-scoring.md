# 自動採点は「在ること」で判定しろ。「無いこと」では判定するな

このファイルは `~/.claude/rules/coding-style.md` の 1 行ポインタから、および eval-harness skill で
採点器（scorer）を書くときに読み込む。元は coding-style.md の常時ロード節だったものを移設した。

自由文の出力を機械で採点するとき、**禁止語・禁止正規表現・混入検査は、正しい回答を落とす。**
説明文が禁止対象に触れるからだ。触れることと、それを答えとして提示することは別物なのに、
文字列検査は区別できない。

```python
# WRONG: 「間違いが無いこと」で判定する
"must_not": ["68名"]            # 「68名は訂正前なので使いません」と正しく説明した回答が落ちる
"must_not_re": [r"[0-9]+\s*%"]  # 「成約率 ＝ 件数 ÷ 分母 × 100 ％」という式の説明が落ちる
english_check(text)            # ケース自身が exact_keys で要求した employees が「英語混入」になる
```

```python
# CORRECT: 「正しい振る舞いが在ること」で判定する
"must_any": ["算出できません", "含まれていません"]   # 正しく指摘したことを直接見る
"json_values": {"employees": 82}                    # 構造化された答えは構造で照合する
```

**規則:**

1. **構造で見られるものを本文の文字列検査で見るな。** JSON / 表 / 数値フィールドは、
   パースして値を突き合わせる。本文に何と書いてあるかは判定に使わない。
2. **禁止検査は、正の検査だけでは通ってしまう場合にのみ足す。**
   正の検査（`must` / `must_any`）が正しい振る舞いを直接捉えているなら、
   禁止検査は冗長で、害だけが残る。
3. **禁止検査を足すなら、断定形に限定しろ。**「Xは◯◯だ」の形だけを拾い、
   言及・説明・式の提示は拾わない。範囲を広げた瞬間に説明文を巻き込む。
4. **採点器が落とした回答は、必ず現物を読め。** 落ちた件数だけ見て「モデルが弱い」と
   結論するな。落ちた理由が採点器側にあるケースが実際に多い。

**痛点**: 2026-08-25から26にかけて、まったく同じ構造で**3回**踏んだ。
1回目は英語混入の許可リスト漏れ（自然な日本語のTCO説明が落ちた）。
2回目は禁止語が正しい説明文を拾った。3回目は、その教訓を書いた直後に、
ケース自身が要求しているJSONキー名を「英語混入」として落とし、
同時に禁止正規表現がまた式の説明を拾った。

**個別パターンを直す対処を3回やって3回とも漏れた。** 直すべきは判定の向きだった。
「間違いを探す」設計をやめて「正しさを確かめる」設計にした時点で、両方消えた。

4回目 (2026-08-28)、対象がコードではなく**プロセス**でも同じことをした。
どのプロセスが定期タスクのものかを、RSSの大小という相関で分類した (「小さい=定期」)。
実測すると定期セッションは 225MB にも 620MB にもいて、分類は成り立たなかった。
正しい判定は、セッション記録に `<scheduled-task name=...>` が**在るか**を見ることだった。
さらにその marker を `name="` で grep して全件を取り逃した。jsonl の中では
`name=\"...\"` とエスケープされている。**相関で分類するな。印が在ることを見ろ。**

これは Self-Verification の burn と同じ形をしている。「ルールを書いた」と
「ルールが守られている」が別の状態であるように、「採点で落ちた」と
「回答が間違っている」も別の状態だ。
