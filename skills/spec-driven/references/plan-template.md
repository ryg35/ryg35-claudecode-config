## 10. リスクと未決事項

### リスク

| ID | リスク | 影響 | 対策 | 検証 |
|---|---|---|---|---|
| R-1 | | 高 / 中 / 低 | | <T-0NN> |
| R-2 | | | | |

**検証欄には tasks.md の T番号を書く。** 「注意する」は対策ではない。
解消したら行頭に打ち消し線を引き、**解消済み (<日付>)** と実測結果を残す。消さない。

### 未決事項

| ID | 論点 | 決定 |
|---|---|---|
| Q-1 | | <未決 / 決定内容と決定日> |
| Q-2 | | |

**解除条件を書いた Q だけ、未決のまま tasks.md へ持ち越してよい。** 書式は「未決 (<いつ / 何が終わったら決まるか>)」。
解除条件の無い Q が1つでも残っていたら、tasks.md に進まない。空欄の「未決」は保留ではなく放置で、
その判断は実装者の推測で黙って確定する。

実績: repo-A `002/plan.md` は Q-1〜Q-5 を未決のまま tasks へ進めている。
`Q-5 | README と spec 001 の書き換え | 投げ先の表に3行目を足すか、章ごと書き直すか` のように
**何が決まればその Q が閉じるのかを書いて登録する**のが、黙って進むのとの違い。

1. **Pre-mortem**: 3か月後にこの計画が失敗しているとしたら、原因は <R-N> である可能性が最も高い。<なぜか。それに対して何を最初に検証するか>

2. **Ambiguity**: <残っている曖昧さ。§10 の Q-N のうち未決のもの。「無い」なら「無い」と書く>
   設計だけが崩れて spec が動かないとき (SKILL.md §7.1 の「どこまで戻るか」で plan から再開する場合) は、spec.md の仕様変更ログに書かない。設計の試行錯誤でログを埋めると、要件の変更履歴が読めなくなる。その判断はここに残す。

3. **Rejected alternatives**: <§1 で棄却した選択肢と、棄却の決め手を1行ずつ>

4. **Rollback path**: <失敗したときに戻せるか。マイグレーション、非可逆な操作、フェーズ単位のコミット分割>

5. **Not-tested**: <自動テストで担保しない範囲。実機確認に回すもの。主観判定に頼るもの>

6. **Confidence**: high | medium | low。<その根拠>

**Confidence は実測で更新する。** 未検証のリスクが理由で medium にしたなら、
該当する spike タスク (T-0NN) が終わった時点で書き換え、更新日と実測値を残す。
実際に 001 は「Brave Shields が localhost を遮断するか未検証」を理由に medium で始まり、
T-005 の実測で通ったので high に上げている。判断の履歴が残るのはここだけ。
