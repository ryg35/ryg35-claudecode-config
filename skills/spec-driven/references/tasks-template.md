## 凡例

- **状態**: `未着手` / `進行中` / `完了 (YYYY-MM-DD)` / `廃止 (YYYY-MM-DD)` の4値のみ。他の語を足さない
- **difficulty**: S (30分以内) / M (1〜3時間) / L (半日以上)
- **種別**: `test` / `impl` / `setup` / `spike` / `manual` / `doc`
- **並列マーカー `[P]` は使わない。** 並列可否は「タスク一覧」の依存列と、末尾の
  「並列実行できる組み合わせ」で表す。見出しに `[P]` を書くと依存列と同じことを
  2箇所で言うことになり、依存が変わったとき片方だけ直る

## タスク一覧

**このファイルの機械可読な情報は、すべてこの表にある。** 個別タスクのブロックには散文だけ置く。

| T | 状態 | 種別 | difficulty | 依存 | トレーサビリティ |
|---|---|---|---|---|---|
| T-001 | 未着手 | setup | S | なし | FR-001 |
| T-002 | 完了 (2026-08-17) | test | M | T-001 | FR-002, AS-1 |
| T-003 | 廃止 (2026-08-18) | impl | M | T-002 | FR-003 |
| T-004 | 進行中 | impl | S | T-002 | US-1, FR-002 |

欄の決まり。

- 状態は上の4値だけ。`保留` `やらない` `done` を発明しない
- **トレーサビリティ列が要件とタスクの対応の正。** 末尾の「トレーサビリティ表」はこの列の転置なので任意節
- 列に書ける ID は `US-N` / `AS-N` / `FR-00N` / `SEC-N` / `SC-N` (Success Criteria) /
  `EC-N` (Edge Cases) / `ASM-N` (Assumptions) の7種類。**受入基準そのものである SC を落としやすい**
- トレーサビリティが無いタスク (足場・仕上げ) は「なし」と書く。空欄にしない
- 依存が複数あるときはカンマ区切り (`T-002, T-005`)

**なぜ表に寄せたか。** 同じ情報を表と個別ブロックの両方に置くと、片方だけ直る。
種別 / difficulty / 依存 / トレーサビリティ はこの表が単一ソース。ブロックには書かない。
実績で完了マーカーが1つも無いのは規律の問題ではなく、状態を書く欄が無かったから
(repo-A 001 + 002 の90タスク、完了マーカー0件)。

### Brownfield の Phase 0 (既存コードに手を入れるとき)

現状の挙動が仕様化されていないコードを触るなら、この2本を先頭に置く。

| T | 状態 | 種別 | difficulty | 依存 | トレーサビリティ |
|---|---|---|---|---|---|
| T-001 | 未着手 | spike | M | なし | なし |
| T-002 | 未着手 | test | M | T-001 | なし |

- T-001 は現状の挙動を実測する。完了条件は `docs/<topic>-eval.md` に記録すること
- T-002 は現状の挙動を固定するテスト。**GREEN で始まる唯一の例外**

通常のタスクは RED で始まる (下の TDD 規約)。この2本だけが例外。
現状を壊していないと言える土台が無いまま改修に入ると、
「直したつもりが別の何かを壊した」を検出する手段が無い。

### 廃止したタスクの扱い

要件が消えてタスクが不要になったときの手順。必ず 1 と 2、任意節を置いているなら 3 も触る。

1. タスク一覧の状態を `廃止 (YYYY-MM-DD)` にする。**行は消さない。**
   消すとトレーサビリティ列と依存列が片側だけ壊れる
2. 末尾の「並列実行できる組み合わせ」からは、その T番号を**削る。ここだけは削る**
3. 任意節の「トレーサビリティ表」を置いているときだけ、該当行も消さず担当タスク欄を `廃止 (YYYY-MM-DD)` にする

**2 を削り忘れると何が起きるか。** 廃止タスクが並列で起動され、executor が廃止済みの要件を
丁寧に TDD で実装する。しかも廃止 ID がトレーサビリティ列に残っているほうが、analyze ゲートの
「spec.md の全 ID が列に出るか」検査は通る。検査が事故を守る形になる。

## TDD 規約 (厳守)

**実装タスクの前に、必ず対応するテストタスクを完了させる。**
テストを書く前に実装コードを書いたら、そのコードは消して書き直す。例外なし。

各テストタスクの完了条件は「テストが**失敗する**こと (RED)」。
テストが最初から通ってしまう場合、テストが対象を検証できていないので書き直す。
各実装タスクの完了条件は「対応するテストが**通る**こと (GREEN)」。

`manual` / `setup` / `spike` / `doc` 種別、および `plan.md` §8.1 の配線層はこの規約の対象外。
配線層は `docs/manual-test.md` のチェックリストで担保する。
Brownfield の Phase 0 (上記) の現状固定テストも対象外で、GREEN で始まる。

## トレーサビリティ表 (任意)

**この表は「タスク一覧」のトレーサビリティ列の転置。同じ写像を2箇所に持つので、片方を直し忘れる。**
逆引き (要件 → どのタスクが担当か) を人が引く必要が出る規模のときだけ作る。作らないなら節ごと消す。
作った場合も**正は一覧表の列**で、この表は検算用。列を直したらこちらも直す。

| 要件 | 担当タスク |
|---|---|
| US-1 <要約> | T-006〜T-013 |
| US-2 <要約> | |
| AS-1 <要約> | |
| FR-001 <要約> | |
| FR-002 <要約> | |
| FR-003 <要約> | 廃止 (2026-08-18) |
| SEC-1 <要約> | |
| EC-1 <要約> | |
| SC-1 <要約> | |
| ASM-1 <要約> | |
| Q-N <論点> | |

**spec.md の全 ID が、一覧表のトレーサビリティ列に1回以上出ること。** 出ていない ID は、実装されないまま出荷される。
逆に、列に無い ID を tasks が参照していたら、spec.md 側の書き漏らし。analyze ゲート (SKILL.md Step 6 の1点目) が見るのも列。

**廃止した要件の行も消さない。** 担当タスク欄を `廃止 (YYYY-MM-DD)` に書き換えるだけ。
消すと、その ID が「まだ実装されていない」のか「もう要らない」のかが区別できなくなる。
