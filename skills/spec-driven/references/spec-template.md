### EARS 6パターン早見表

| # | パターン | 型 | 例 |
|---|---|---|---|
| 1 | Ubiquitous (常時) | システムは <応答> すること | システムは、投げ先をパネルに常時表示すること |
| 2 | State-driven (状態駆動) | <状態> のあいだ、システムは <応答> すること | 翻訳中のあいだ、システムは進捗を段落数で表示すること |
| 3 | Event-driven (事象駆動) | <トリガー> したとき、システムは <応答> すること | 利用者が拡張アイコンを押したとき、システムは確認ダイアログを表示すること |
| 4 | Optional feature (機能任意) | <機能> を搭載している場合、システムは <応答> すること | クラウド投げ先が有効な場合、システムは送信前に外部送信を告知すること |
| 5 | Unwanted behaviour (異常系) | もし <条件> の場合、システムは <応答> すること | もし本文を検出できなかった場合、システムは「本文が検出できませんでした」と表示すること |
| 6 | Complex (複合) | <状態> のあいだに <トリガー> したとき、システムは <応答> すること | 翻訳中に利用者が再実行したとき、システムは前の処理を優先し中断可否を確認すること |

日本語で書く場合の注意。

- **トリガー節 + 主語 + shall 相当の述語**の順を崩さない。述語は「〜すること」で統一する
- **主語を省略しない。** 「エラーを出す」ではなく「システムはエラーを表示すること」。
  日本語は主語を落とせるので、誰が何をするのかが消えたまま実装に渡る事故が起きる
- 「〜してはならない」も述語として認める (禁止要件)。例: 「システムは本文を文字列連結で埋め込んではならない」
- 1つの FR に「かつ」で2つの要求を詰めない。分ける

## 仕様変更ログ

(なし)

**変更するときは3つで1セット。**

1. 本文を新しい内容に更新する
2. 該当箇所の直下に、引用ブロックで変更前の原文と変更日を残す
3. この節にエントリを追加する

本文が常に唯一の仕様。この節は履歴。
1 だけやると履歴が消える。3 だけやると本文が嘘になる。

**実績で 3 だけやった事故が出ている。** repo-B
`specs/002-remote-mcp-and-cloudflare/spec.md` は、同じファイルの26行目が「US-2 を含む」、
80行目が「含む: US-1 / US-2 / US-3 / US-4」、89行目が「US-2 は次イテレーションに延期」と
主張している。ログだけ足して本文を直さなかった結果。

本文に残す引用の書き方 (repo-A 001 の形)。

```markdown
> 上の4項目は 2026-08-16 に変更した。変更前は1行で
> 「翻訳エンジンは local LLM を使う。クラウド API には投げない」だった。
> 経緯は下の「仕様変更ログ」を参照。
```

### エントリの雛形

```markdown
### YYYY-MM-DD ... <一行で何が変わったか> (<変わった節名>)

**影響 ID**: <FR-003, AS-2 のようにカンマ区切り。無ければ「なし」>
**種別**: <追加 | 訂正 | 廃止 | 移動 から1つだけ>

**変更前**

> <本文から移してきた原文をそのまま引用する>

**変更後**: <本文のどこを見ればよいか。本文が唯一の仕様なので、ここに仕様を書き直さない>

**理由**: <実測値 / ユーザー決定 / 外部制約 のいずれか。
実測なら数値と `docs/<topic>-eval.md` への参照を書く>

**この変更で増えた約束（または減った約束）**

- <増えたもの>
- ~~<減ったもの。打ち消し線で書く>~~
```

雛形の欄の決まり。

- **「影響 ID」と「種別」の2行は必須。** この2行があるから、analyze ゲートが
  `grep -A1 '影響 ID'` で変更済み ID を機械的に列挙できる。1行でも欠けたら目視に戻る
- **種別が `移動` のときは、移動先の `specs/<NNN>-<slug>/` を必ず書く。**
  書かないと、この spec だけを読んだ人が「この要件は消えた」と誤読する
- **種別が `廃止` のときは、tasks.md の該当タスクの状態も `廃止 (YYYY-MM-DD)` にする。**
  spec 側だけ廃止にすると、tasks 側に生きたタスクが残って実装される
- 減った約束は行ごと消さず、打ち消し線で残す。消すと「なぜこの制約が無いのか」を後から追えない
- 理由が実測なら数値を書く。「速かったので」ではなく「39秒 対 170秒」
- ここでいう「種別」は仕様変更の種別。tasks.md の種別 (`test` / `impl` / `setup` / `spike` /
  `manual` / `doc`) とは別物
