# PROJECT-SEED.md — Project Documentation Best Practices

Canonical template and placement rules for generating a new project's documentation set. Used by the `project-doc-gen` agent and the `/project-init` command. This file is the single source of truth for:

- Standard `docs/` layout
- Root-level files (`CLAUDE.md`, `README.md`, `.claude/settings.local.json`)
- Generation rules (naming, encoding, skeleton-first, overwrite policy)
- CLAUDE.md / settings template bodies

Keep this file generic. Project-specific content belongs inside the generated project, not here.

---

## Core Principles

1. **Never overwrite existing files.** Always check existence before writing. Skip any file listed in `project-context.json.existingFiles`.
2. **Skeleton-first.** Initial generation produces section headings + placeholders. Details accrue as the project grows.
3. **One document, one responsibility.** Avoid content duplication; link to the authoritative doc from others.
4. **Accurate, not aspirational.** Only write what can be justified from `project-context.json` or existing source. Never guess.
5. **kebab-case filenames, UTF-8 encoding.**
6. **`mode=existing` scans first.** Read `package.json`, `tsconfig.json`, `pyproject.toml`, `src/`, etc. before writing anything.
7. **Every non-trivial change updates docs in the same PR.** Enforced via the pre-commit-push-docs hook.

## Standard `docs/` Layout

### Required for every project

| File | Contents |
|------|----------|
| `docs/folder.md` | Folder structure under `docs/` and each folder's role |
| `docs/folder/folder.md` | Repository-wide folder structure and responsibilities |
| `docs/overview/project-summary.md` | Purpose, target users, success criteria |
| `docs/requirements/requirements.md` | Functional / non-functional requirements, constraints (skeleton) |
| `docs/architecture/architecture.md` | Architecture overview (generated by the `architect` agent; supplement if incomplete) |
| `docs/tech-stack/stack.md` | Technologies, versions, rationale |
| `docs/testing/test-strategy.md` | Test levels, execution steps, pass criteria |
| `docs/env/env-vars.md` | Environment variables — name, purpose, required/optional |
| `docs/deployment/deploy-runbook.md` | Deployment steps, based on deployment target |
| `docs/setup/local-setup.md` | Local setup steps, prerequisite tools |

### Required when the project exposes an API

| File | Contents |
|------|----------|
| `docs/api/api-spec.md` | API list, input/output, error specifications (skeleton) |
| `docs/database/schema.md` | Tables, columns, relations, constraints (skeleton) |
| `openapi.yaml` (root) | OpenAPI 3.0 specification (skeleton) |

### Required when the project has a UI surface

| File | Contents |
|------|----------|
| `docs/ui/components.md` | Component inventory and design-system reference |
| `tests/e2e/` + `playwright.config.*` | Scaffolded by the `e2e-runner` agent during `/project-init` Phase 3.5 |

### Generated on demand (not at init)

| File | Generated by | When |
|------|--------------|------|
| `docs/codemaps/architecture.md` | `/update-codemaps` | After structural changes |
| `docs/codemaps/backend.md` | `/update-codemaps` | After backend structural changes |
| `docs/codemaps/frontend.md` | `/update-codemaps` | After frontend structural changes |
| `docs/codemaps/data.md` | `/update-codemaps` | After schema / data-model changes |
| `docs/CONTRIB.md` | `/update-docs` | When `package.json` scripts change |
| `docs/RUNBOOK.md` | `/update-docs` | When deployment / ops steps change |
| `docs/plan/<feature>.md` | `/plan` | Before any non-trivial implementation (lifecycle: `backlog` → `active` → `in-progress` → `done`; on `done` the file is moved to `docs/plan/done/<feature>.md`) |
| `CHANGELOG.md` (root) | `/changelog` | Before releases |

## Root-Level Files

### `CLAUDE.md` template

```markdown
# Project: <Project Name>

## Overview
<Description of purpose — 1-3 sentences>

## Tech Stack
<Tech stack list — language, framework, DB, cache, deployment>

## Project Structure
<Directory tree — top 2-3 levels>

## Development Rules
- Update documents under `docs/` simultaneously with implementation changes
- When changing the DB, keep `docs/database/schema.md` up to date and leave history in `migrations/`
- Match branch names with the content of changes (`feat/…`, `fix/…`, `docs/…`, etc.)
- Use conventional commits format for commit messages
- `docs/plan/<feature>.md` must include the YAML header (status, branch required; completed: YYYY-MM-DD added on done) defined in `~/.claude/templates/plan/`

## Key Files
- `docs/folder.md` — docs/ folder structure
- `docs/architecture/architecture.md` — architecture overview
- `docs/requirements/requirements.md` — requirements definition
- `docs/tech-stack/stack.md` — tech stack and rationale

## Commands
- `/plan` — create implementation plan
- `/tdd` — test-driven development
- `/vibe` — full pipeline from pull to PR
- `/commit-push` — safe commit & push procedure
- `/update-docs` — sync docs from source of truth
- `/update-codemaps` — refresh architecture codemaps
- `/e2e` — generate and run Playwright tests (UI projects)
```

### `SECURITY.md` template

Place at repository root. Skip if a `SECURITY.md` already exists. Body in Japanese (per language policy). Fill `<contact-email>` from interview if collected; otherwise leave a `TODO` placeholder for the user.

```markdown
# セキュリティポリシー

本リポジトリ (`<project-name>`) のセキュリティに関する報告窓口と対応プロセスを定めます。

## サポート対象

セキュリティ修正を提供するのは `main` ブランチの最新リビジョンのみです。過去のタグやリリースに対する遡及的な修正は行いません。

| バージョン | サポート |
| --- | --- |
| `main` (最新) | あり |
| それ以外 | なし |

## 脆弱性の報告先

**公開 Issue / Pull Request では報告しないでください。** 内容が公開されることで悪用される恐れがあります。

報告は以下のいずれかの方法で行ってください。

1. **メール**: `<contact-email>` 宛に「`[SECURITY] <project-name>`」を件名に含めて送付
2. **GitHub Private Vulnerability Reporting**: 本リポジトリの "Security" タブ → "Report a vulnerability" から非公開で報告

## 報告に含めてほしい情報

- 影響を受けるコンポーネント
- 再現手順 (最小再現コードや HTTP リクエスト例があると助かります)
- 想定される影響範囲 (情報漏洩 / 認可バイパス / RCE など)
- 報告者の連絡先 (返信先メールアドレス)
- 既に CVE 等が発番されている場合はその ID

## 対応プロセスと SLA

報告を受け取った後の対応目安 (営業日基準):

| ステップ | 目安 |
| --- | --- |
| 受領確認の返信 | 3 営業日以内 |
| 影響範囲・深刻度の初期評価 | 7 営業日以内 |
| 修正パッチの提供 / ワークアラウンド共有 | 深刻度に応じて 7〜30 日 |
| 公開ディスクロージャ調整 | 修正リリース後、報告者と協議のうえ |

深刻度は CVSS v3.1 を参考に Critical / High / Medium / Low で評価し、Critical / High を優先対応します。

## セーフハーバー

善意に基づく研究目的の調査で、本ポリシーに従って非公開で報告された場合、当方から法的措置を取ることはありません。ただし以下を満たしてください。

- 個人情報や本番データへの不要なアクセス・取得・改ざんを行わないこと
- サービス可用性に影響を与えないこと (DoS 等を行わないこと)
- 報告内容を修正リリース前に公開しないこと
```

### `.github/dependabot.yml` template

Place at `.github/dependabot.yml`. Skip if it already exists. Adjust `package-ecosystem` and `directory` per the actual project layout.

```yaml
version: 2
updates:
  # Replace with the actual ecosystem (npm / pip / cargo / gomod / etc.) and directory
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
      day: "monday"
      time: "09:00"
      timezone: "Asia/Tokyo"
    open-pull-requests-limit: 5
    labels:
      - "dependencies"
    commit-message:
      prefix: "chore(deps)"
      include: "scope"
    groups:
      dev-dependencies:
        dependency-type: "development"

  # Always include GitHub Actions
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "weekly"
      day: "monday"
      time: "09:00"
      timezone: "Asia/Tokyo"
    open-pull-requests-limit: 3
    labels:
      - "dependencies"
      - "ci"
    commit-message:
      prefix: "chore(ci)"
      include: "scope"
```

### `.claude/settings.local.json` template

```json
{
  "permissions": {
    "allow": [],
    "deny": []
  }
}
```

Populate `allow` based on the detected tech stack — frequently used commands for `npm` / `pnpm` / `bun` / `pytest` / `go test` / `cargo test` / etc. Do not add destructive commands.

## Generation Rules (strict)

1. **Use kebab-case** for all filenames (`project-summary.md`, not `projectSummary.md`).
2. **One document, one responsibility** — link rather than duplicate.
3. **Initial version is skeleton only** — section headings + placeholders, details filled in later.
4. **Reflect `project-context.json` faithfully** — never write what cannot be justified by input.
5. **UTF-8 only.**
6. **Check existence before writing** — use `Bash("ls <path>")` or `Read`; if the file exists, skip and log the skip.
7. **For `mode=existing`**, read the actual code (package.json, tsconfig.json, pyproject.toml, src/, etc.) first. Generated docs must reflect the real state, not assumptions.
8. **Never invent metrics.** Coverage / performance numbers only when measured.
9. **Stable anchors.** Use `# Heading` consistently so cross-links don't rot.
10. **Language policy follows the user's global CLAUDE.md** — documentation body in Japanese, identifiers and frontmatter in English.

## Agent Split (who owns what)

| Agent | Owns | Timing |
|-------|------|--------|
| `project-doc-gen` | Initial generation of the full `docs/` set + root files | `/project-init` only |
| `architect` | `docs/architecture/architecture.md` drafts | `/project-init` Phase 2, `/plan` Phase 0.5 |
| `doc-updater` | Ongoing updates to existing docs + codemaps | `/update-docs`, `/update-codemaps`, `/vibe` Phase 7, `/review-prs` Step 5 |
| `ci-gen` | `.github/workflows/*.yml` (including `e2e.yml` for UI projects) | `/project-init` Phase 3 |
| `e2e-runner` | Playwright scaffold (config + smoke spec + POM) | `/project-init` Phase 3.5 (UI only) |

`project-doc-gen` generates skeletons. `doc-updater` evolves them. Never cross these responsibilities.

## Usage Inside the `project-doc-gen` Agent

Reference this file from the agent prompt like:

```
Template reference: ~/.claude/templates/PROJECT-SEED.md
```

Do **not** copy the entire template body into project-doc-gen.md — read this file at runtime instead. Keep this file as the single source of truth so updates propagate automatically.
